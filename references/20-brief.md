# 보고서 작성 규칙 ③ 브리프 · 요약 · 추진계획(안)

> **선독 순서**: `00-common.md`(공통)를 먼저 읽고 이 파일을 읽는다. 공통 규칙과 겹치면 이 파일이 이긴다. 발주처 양식이 있으면 양식이 이긴다.
> **적용 대상**: 연구결과 요약본 · 정책브리프·이슈페이퍼 · 추진계획(안)·기획(안) · 보고자료(부처 보고용) · 1페이저 · 과업수행계획서 · 회의자료
> **근거**: 저자 최종본 10건 계량(정책연구보고서 A 요약본 초안→최종 · 기획(안) F 기관 초안→저자 보완본 · 기획보고서 G의 보고자료·컨셉 1쪽 · 추진계획(안) M 초안→최종 · 계획(안) N 등) · 부처 브리프 양식 규격 · 발주처 연구개발계획서 양식 실측 · 작업 세션 피드백 채굴
> **압축 작업**(긴 보고서 → 브리프)은 보고서 압축 절차(별도 도구가 있다면 그 절차)를 따르고, 문체·서식은 이 파일을 따른다.

브리프는 **읽는 사람이 1~2분 안에 판단하도록 만든 문서**다. 연구보고서보다 줄이 짧고(중앙값 40~60자), 결론이 앞에 오고, 라벨과 결론줄이 뼈대를 대신한다.

---

## 1. 머리와 골격

### 1.1 머리 두 줄
```
「과제명」 문서유형(안)
(2026. 9. 23.(수), 작성자 또는 기관명)
```
- 저자 문서 전반에서 반복된 형식이다. 기관 초안의 `<'YY.MM.DD(요일), 기관>` 형식은 저자 수정본에서 이 형식으로 바뀌었다

### 1.2 유형별 골격
| 유형 | 골격 |
|---|---|
| **요약본·정책브리프** | 핵심 메시지(두괄) → 배경·문제 → 현황·쟁점 → 핵심 근거 → 제언(우선순위 3~5) → [붙임] |
| **추진계획(안)** | 추진 배경 → 현황·문제점 → 추진 방향(목표 두괄) → 세부 추진계획 → 추진체계·일정 → 향후 계획 |
| **기획(안)** (신규사업) | 추진 배경 → 환경 분석 → 사업 개요(표) → 핵심 질문표 → 세부 내용 → 추진체계 → 기대효과 |
| **보고자료**(부처 보고) | 개요 표 → 핵심 쟁점 → 대응 방안 → 향후 계획 · 요청 사항. 정책 보고의 공공 표준 구성은 보고개요 → 현황 및 문제점 → 정책수단·대안 → 추진계획 → 건의 → 행정사항(길잡이 p.83) |
| **과업수행계획서** | RFP 요구 → 수행 전략 → 방법론 → 추진체계·연구진 → 일정 → 산출물 |
| **회의자료** | 회의 개요 → 논의 안건(안건별 쟁점·판단 요청) → 향후 일정. 회의 내용과 참고 자료를 분리한다(길잡이 p.84) |
| **회의결과 보고** | 회의 개요 → 회의 결과(총괄·안건별) → 후속 조치 → 부록. 발언은 객관적으로 정리(길잡이 p.85) |
| **상황·정보 보고** | 상황: 개요 → 사실 기술 → 부연 설명 → 간략한 의견·대책 / 정보: 개요 → 실태·상황 → 평가·의견(길잡이 p.84) |

- 흐름은 **배경 → 문제 제기 → 그래서 무엇을 하려는가**로 자연스럽게 이어져야 한다(저자 피드백)
- 핵심 요약(TL;DR)은 맨 앞 박스로 둔다. 요약은 표지나 첫 쪽 맨 위에 두어 가장 먼저 읽히게 한다(IDRC 원문). 목적을 글의 앞부분에 분명히 밝히고, 권고는 실행 가능하게 쓴다(ODI, Jones·Walsh 2008, p.4·6)
- 목록은 5~7개 안팎으로(IDRC 원문: 너무 짧으면 무의미해 보이고 너무 길면 부담스럽다)
- **핵심을 10~20초 안에 말할 수 있어야** 하고, 이 문서로 상대에게서 받을 결정이 무엇인지 알고 쓴다(『정책기획 실습』 p.83)
- 문서 제목에 **내용과 방향**이 담긴다("○○ 개선방안", "○○ 구축 계획"). 제목은 가능하면 1줄(길잡이 p.82)
- 본론은 **중요도가 높은 사항부터**, 대안은 '어떻게'가 드러나게(길잡이 p.82)
- 한 건은 한 장에("1건 1매 주의", 편람 p.76)
- 1페이지 보고서는 무엇을 문서에 넣고 무엇을 구두·붙임으로 돌릴지 먼저 정한다

## 2. 문체와 위계

| 항목 | 규칙 | 근거 |
|---|---|---|
| 종결 | **명사형 종결 85~100%** — `~함 / ~임 / ~있음 / ~필요 / 명사`. 본문 "다." 0건 | 저자 최종본 4건 |
| 줄 길이 | 한 줄 중앙값 **40~60자**. `□` 요지 줄은 1문장 60~120자까지 | 저자 최종본 3건 / 발주처 계획서 양식 실측 |
| 위계 | `□` → `ㅇ/○` → `-` → `*`. 부처·발주처 양식이 `ㅇ`이면 `ㅇ` | 저자 최종본 3건 |
| 라벨 | `□ (라벨) 한 줄 주장` → `○ (라벨) 근거` 이중 라벨. 라벨 줄 20~30%(양식 문서는 70%대) | 저자 최종본 3건 |
| 결론줄 | 절 끝은 `⇨` 또는 `☞` 한 줄로 닫는다 | 저자 최종본 3건 |
| 보충 | 사례·정의는 `* 예: …`, 단서·예외는 `※` 줄로 본문 밖에 뺀다. `※`에 주장·근거를 넣지 않는다 | 저자 최종본 3건 / 부처 브리프 양식 |
| 번호 강조 | 핵심 항목은 `➊ ➋ ➌` 명사구 헤드라인으로 분리하고 `○` 설명, `-` 보충 | 저자 최종본 3건 |
| 연도·금액 | `'28년`, `'23~'27` 축약, `억원`. 한자 약어(高·現·↑) 허용 | 저자 최종본 2건 |
| 볼드 | **양식을 따른다.** 부처 브리프 양식은 핵심 수치·`(라벨)` 볼드가 핵심 장치(문단당 3~4곳 이내), 발주처 계획서 양식은 볼드 없이 라벨 줄이 강조 | 부처 브리프 양식 / 발주처 계획서 양식 |
| 캡션 | 표 위 `< 제목 >`. 번호 상호참조가 많으면 `< 표 N. 제목 >` | 부처 브리프 양식 / 발주처 계획서 양식 |
| 출처 | 문장 안 괄호 `(기관·「자료명」)`, 표 아래 `* 출처: …` 한 줄. 각주 없음 | 발주처 계획서 양식 / 저자 최종본 |

- **개조식이어도 각 꼭지의 설명은 충분해야 한다** — "개조식이지만 각 꼭지마다 설명이 충분해야 돼. 지금은 너무 짧아서 이해하기 어려움"(저자 피드백). 키워드만 있는 줄은 합쳐 문장으로 만든다
- 반대로 **문장을 대시로 이어 한 줄에 두 문장**을 넣지 않는다(공통 §3.3)

## 3. 계획형 문서의 급소

### 3.1 아직 안 한 일이다
- 계획서·기획(안)은 **아직 하지 않은 일의 계획**이다. 결과를 이미 얻은 것처럼 쓰지 않는다
- 제안 중인 것을 "확정·완성"으로 쓰지 않는다 — "이미 확정한 건 아니고 제안 중인데"(저자 피드백)
- 수치 목표는 `20개 내외`, `(안)`으로 두고 **`※` 줄에 전제·한계**를 밝힌다
  - A: "빅데이터 AI로 공백기술 20개를 지정"
  - B: "20개 내외를 기획하되, 공백·병목 근거와 실제 수행 여건이 충족되는 범위에서 지원대상을 확정" + "※ 후보 수는 기획 목표로 운영하고 데이터만으로 기술의 필요성을 확정하지 않음"

### 3.2 무엇을 하겠다는지 구체적으로
- 모호한 추진 방향 문장 금지 — "계획서니까 명료한 문체 + 뭘 하겠다는 건지 구체적으로"(저자 피드백)
- 추진 방향 첫 블록 = **과업 목표 두괄식 + RFP 요구 전체를 괄호로 나열**. 차별성은 결과가 아니라 **설계 원칙**으로 쓴다
- **RFP·발주처 요구를 충실히 수행하는 전략이 먼저**다. 제안 단계에서 만든 자기 설계안에 집착하지 않는다(저자 피드백)
- 추진 전략은 수행 역량으로 입증한다 — 꼭 필요한 전문성을 갖춘 연구진 + 워킹그룹·자문위원회
- **절차는 방안이 아니다**: "TF 구성·의견수렴·검토"만 적힌 칸은 빈칸과 같다. 무엇을 바꾸는지를 쓴다(『정책기획 실습』 p.84)
- 추진계획에는 **시기·기한·담당·협조 기관·단기/중장기** 구분을 넣는다
- 방안을 단순 나열하지 말고 시기·내용·수단으로 나눠 체계화한다(길잡이 p.94)
- `추진 배경 및 목적`은 배경과 목적을 따로 쓴다(길잡이 p.93)

### 3.3 기획(안)은 차별성이 생명
- "사업 컨셉이 차별성이 있어야 예산을 딸 수가 있지"(저자 피드백). 대안이 여럿이면 **제목에서부터 확실히 달라야** 한다
- 전작·자기 기관 이야기가 아니라 **"이 사업이 왜 필요한가"** 에 초점(저자 피드백)
- 필요하면 **핵심 질문표**: 왜 필요한가 / 무엇이 다른가 / 무엇을 남기는가 → 본 사업의 답
- 개념이 새로우면 **정의표**(용어 | 정의 | 판단 기준)를 앞에 둔다

### 3.4 추진계획(안)의 장치
- 연차별 상태 태그 `(완료) · (진행중) · (예정)`
- `< RFP 세부항목별 1·2차년도 대응 현황 >` 대응표
- 산출물은 `▷ (산출물)` 줄
- 향후 계획은 `○ ('26. 5. 21. 까지) 할 일` 형식
- 개요는 표(사업명·기간·규모·추진체계·대상), 칸 안 글머리는 `√`

## 4. 요약본의 급소
- **자립성**: 요약본만 읽어도 이해되어야 한다. 약어 정의를 버리지 않는다
- **근거를 데리고 간다**: 핵심 수치는 출처와 함께 옮긴다. 원본에 출처가 없는 수치는 싣지 않거나 표시한다
- 본문과 **용어·수치가 한 글자도 어긋나지 않는다**. 본문을 고치면 요약본도 고친다(공통 §1.7)
- 정책 제언은 **한 문장으로 선명하게**(저자 피드백)
- 분량 기준: 정책브리프는 2쪽 안팎이 국제 관례(IDRC: 2쪽·1,500단어 이내), 발주처 양식이 있으면 양식. 서술문은 `사실(수치, 기준연도)` 괄호 압축 + `*` 보조행으로 줄인다
- 내부 파일명·작업 표지(`03_research_boost`, `_강화본`)가 요약본에 새어 나온 사례가 있다(반면교사) — 배포 전 전수 검색

## 5. 짧은 전달문(요청·안건·메일 본문)
- **요청 사항은 딱 한 줄로** — 무엇을 해 달라는지 먼저. "뭘 해달라는 건지 모르겠음, 묶어서 딱 한 줄로 명확하게"(저자 피드백)
- 메일·메시지는 짧게 핵심만 — "누가 메일을 이렇게 길게 쓰니?"
- 글자·바이트 제한이 있으면 **먼저 확인하고 맞춘다**("4000 byte")
- 답변서·이메일·대중용 안내서는 개조식이 아니라 `~입니다` 정중체(공통 §3.1 장르 표)

## 6. 배포 전 점검

기계 점검 항목은 `scripts/rcheck.py check <파일> --type brief`로 먼저 돌린다.

- [ ] 첫 화면(또는 첫 박스)만 읽어도 결론과 요청이 보인다
- [ ] 명사형 종결이고, 키워드만 있는 줄이나 대시로 이은 두 문장이 없다
- [ ] 절마다 결론줄(`⇨`/`☞`) 또는 요지 줄이 있다
- [ ] 계획형이면 "확정·완성·지정"처럼 결과를 선취한 표현이 없고, 수치 목표에 `※` 전제가 붙었다
- [ ] 무엇을·언제까지·누가 하는지가 구체적이다
- [ ] 요약본이면 본문과 용어·수치가 일치하고, 약어 정의가 살아 있다
- [ ] 볼드·캡션·글머리가 해당 양식(부처 브리프 / 발주처 계획서 / 발주처 지정)과 일치한다
- [ ] 분량·바이트 제한을 지켰다
- [ ] 공통 규칙 `00-common.md` §9 점검표를 통과했다
